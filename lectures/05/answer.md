- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を 5 → 2 に変更（変えたのはこの1か所のみ）。同じ質問で変更前後に `--trace` 付きで実行し、before.txt / after.txt を比較した。
- 比較した質問と、固定した条件（モデル・対象資料など）：「コンパクションとセッションをまたぐメモリの違いは？日々のメモは全部長期メモリになる？」／モデル gemini-3.5-flash-lite、対象資料・質問文・RAG_TOP_K 以外の設定は同一。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

| 項目 | 変更前（TOP_K=5） | 変更後（TOP_K=2） |
|---|---|---|
| search_materials の呼び出し回数 | 1回 | 2回 |
| 検索語 | 「コンパクション セッション メモリ 長期メモリ」 | ①「コンパクション」 ②「日々のメモ 長期メモリ」 |
| 返ってきたページ（traceの先頭） | 第3回 p.65 ほか | ① 第3回 p.65 ほか ② 第3回 p.40 ほか |
| 回答で引用したページ | 第3回 p.13, 38, 39, 40, 65 | 第3回 p.39, 40, 65 |
| 正しい根拠 p.13 / 39 / 40 | 3ページとも引用 | p.13 が抜けた |
| 時間 | 3.80 秒 | 5.53 秒 |
| トークン数（入力 / 出力） | 2,477 / 375（モデル応答 2回） | 3,382 / 498（モデル応答 3回） |
| 推定費用 | $0.001681 | $0.002260 |

  - ※ trace の tool return 行は途中で省略表示されるため、返ってきたページは先頭の page_id と回答中の引用ページで確認した。
- 改善した例と、残る失敗・制約：変更後も回答の大筋（コンパクション＝同じセッション内で履歴を要約して詰める／セッションをまたぐメモリ＝外の保存先に書き出して次回に引き継ぐ／日々のメモは全部が長期メモリになるわけではない）は保たれた。一方で p.13 が取れなくなり、セッションをまたぐメモリの根拠が p.39 だけになった。各1回ずつの実行なので、ばらつきは未確認。
- 気づき・疑問：TOP_K を減らせばトークンと費用も減ると予想したが、件数が減った分を補うためにエージェントが検索を2回に分け、モデル応答も 2回→3回 に増えた。その結果、入力トークンは約1.4倍、費用は約1.3倍、時間も約1.5倍に増えた。件数を絞るだけではコスト削減にならず、正しい根拠ページ（p.13）の取りこぼしも起きる。質問の種類によって適切な TOP_K が違うのか、複数回実行しても同じ傾向になるのかを確かめたい。
